### ★実際の解禁条件（実測。`enemyOnly` フラグではない）
`campaignAircraft()` は **`AIRCRAFT_ORDER.filter(id => campaign.aircraft.has(id))`** であり、
`selectAircraft()` はその結果に含まれるかだけを見る。
つまり自機として飛べる条件は **`AIRCRAFT_ORDER` に載っている ∩ `CAMPAIGNS.rus.aircraft` に載っている**
の2つだけ。**`enemyOnly: true` は読者向けの注釈でしかなく、コードは一切参照していない**
（`AIRCRAFT_ORDER` に無いことが実質的な制約になっている、とコメントにも明記されている）。

### やること
1. **`AIRCRAFT_ORDER` に8機を追加**（現在14機 → 22機）し、**`CAMPAIGNS.rus.aircraft` を10機に**する:
   `mig21, mig23, mig29, mig31, su25, su33, su35, su37, su47, su57`。
   あわせて `enemyOnly: true` の注釈を外す（実害は無いが、嘘の注釈を残さない）。
   **★`CAMPAIGNS.usa.aircraft` は絶対に触るな** — `AIRCRAFT_ORDER` に足しただけでは
   米編のハンガーには出ない（usa側の許可リストで弾かれる）ことを実装で担保している
2. **★ su57 は IRONBACK の乗機であり、露編のプレイヤーは IRONBACK 本人**。
   露編で su57 に乗れるのは物語的に正しい。ただし**性能序列の頂点**なので、
   米編の f22 と同じ扱い（＝最後に解禁される最強機）にすること
3. **性能序列を米編と同じ思想で揃える**（[[memory: sortie-project]] の 2666be8 の決定に従う）:
   露編の序列は `su57 > su35 > su47 > su33 > su37 > mig29 > mig31 > mig23 > mig21`、
   `su25` は攻撃機として別枠（A-10相当。HP294と引き換えに鈍足・低旋回）
   - **su37 の扱いに注意**: 現状 turn 38 で su47(42) より低く su35(37) より高い。
     既に露編で選択可なので、序列に組み込むだけでよい
4. `blurb` の書き換え: 現在は全機「敵の最新鋭制空機〜」という**敵視点**の文になっている。
   露編ではこれが自機選択画面に出るので、自軍視点へ書き直す。
   **調査済み: `blurb` の参照は `ui.aircraftBlurbLine.textContent = spec.blurb`（1箇所）だけで、
   ハンガー画面専用。敵として出撃する側の表示には一切使われていない**
   → キャンペーン別の出し分けは不要で、単純に書き換えてよい

### やらないこと
- **`AIRCRAFT_TYPES` の性能値そのものは書き換えるな。** 自機と敵で共有しているので、
  露編でプレイアブル化した機体の数値を触ると**米編の敵の強さが変わる**
  （ユーザー設計「敵の強さ = 機体性能 × 役割 × AIの賢さ」の第1項を壊す）。
  序列の調整が必要なら `AIRCRAFT_ORDER` の並びとハンガーのバー表示で表現する

## 2. ミッション20本

`docs/spec_campaign_story.md` §3 の対応表がそのまま20本の設計表。**マップ・時刻・天候は
対応する米編ミッションと共通**（同じ戦闘の裏側なので）。

### キー命名
米編が `m01`/`m-heli` 等の混在になっているので、露編は**最初から統一する**: `r01` 〜 `r20`。
（米編のキーは記録の後方互換のため変えない）

### 各ミッションに必須のフィールド
米編の完成形と同じ: `key` / `world` / `title` / `jp` / `act` / `storyNo` / `story` /
`epilogue` / `sequence` / `parTime` / `campaign: "rus"`。
**`storyNo` は配列位置と一致させること**（米編で20/20一致を確認済み。ズレは順序バグの検出器になる）

### ★表裏で噛み合わせる4本（ここだけ設計上の制約がある）
| # | 露編 | 米編との噛み合わせ |
|---|---|---|
| 10 | 補給列車を守る | **守れない**（米編10で列車は破壊される）。積荷は軍需品だったと後で知る |
| 13 | 輸送機を落としに行く | **1機は落とすが取り逃がす**（米編13は「1機失うが残りは守り切る」） |
| 16 | 母艦を沈めに行く | **沈められない**（米編16でINDEPENDENCEは健在） |
| 19 | HANGMANとの決着 | **撃墜に至らない**。被弾して雲へ逃れる（米編19の裏。どちらも「奴は墜ちなかった」） |

**負け確定ミッションをどう成立させるか**: プレイヤーの操作で結果が変わらないのは
ゲームとして悪い。**「目標は達成できるが、物語上の目的は達成されない」形にする**。
例: 露編10は「列車の護衛」ではなく「列車を襲う敵機の撃墜」を目標にし、
規定数を墜としてミッションはACCOMPLISHEDになるが、エピローグで
「それでも列車は失われた」と書く。**ゲームの勝敗と物語の勝敗を分離する**。

## 3. 無線セリフ

- 話者は米編と同じ3系統を流用: `command` → **NORTHSTAR**、`wingman` → **SICKLE 2**、`enemy` → AEF機
- **★米編の敵セリフとの対称性**: 米編で敵（＝IRONBACK側）が言う台詞を、露編では
  プレイヤー側が**言う側**になる。同じ文言を左右反転させると「我は汝、汝は我」が効く
- 恐怖4段階（`fearStageFor`）は米編と同じ仕組みで、**AEF機が恐怖する側**になる
- 日本語で書く（[[memory: language-preference]]）。HUD/UIラベルは英語のまま

## 4. 実装の進め方

**★ペイロード登録方式（`docs/spec_payload_registry.md`）の完成を待ってから着手する。**
米編20本を並列で作った際、閉じ括弧の切り落とし事故を3回踏んでおり、20本を同じやり方で
作れば同じ事故が再発する。payload方式なら各班の成果物が新規ファイル1個になるので
衝突が構造的にゼロになる。

### 班分け（payload方式の初の実戦投入）
4班 × 5本。ACTの切れ目で分けると物語の一貫性が保ちやすい:

| 班 | 担当 | payload |
|---|---|---|
| 1 | ACT1: r01〜r05（攻める） | `payloads/rus_act1.payload.js` |
| 2 | ACT2前半: r06〜r10（押し返される） | `payloads/rus_act2a.payload.js` |
| 3 | ACT2後半+ACT3前半: r11〜r15（焼く側へ） | `payloads/rus_act2b.payload.js` |
| 4 | ACT3後半+ACT4: r16〜r20（失う） | `payloads/rus_act4.payload.js` |

所有権宣言（各班の委譲プロンプトに必ず入れる）:
```
所有（書いてよい）: payloads/rus_<班>.payload.js
参照（読むだけ）  : index.html, docs/spec_rus_campaign.md, docs/story_bible.md,
                    docs/spec_campaign_story.md
禁止（触るな）    : index.html への書き込み / git commit / ポート8340
```

合流はメインループが `tools/inline_payload.mjs` を**1班ずつ**実行し、
各回 `tools/registry_gate.mjs` を通す（まとめて入れると壊した犯人が特定できない）。

### 着手順
1. §1のプレイアブル機拡充（index.html直接編集・直列・1委譲）
2. `CAMPAIGNS.rus` の `locked` を false にする（20本が揃ってから。途中で開けると空の編が見える）
3. §2の20本を4班並列
4. 両編クリア後の締め（story_bible §5「我は汝、汝は我」）— 最後・単独タスク
